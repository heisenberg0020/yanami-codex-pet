# 验收与迭代

验收对象是一个内容哈希明确的候选包。任何素材变化都会产生新候选；旧结果不能自动继承。**自动检查、预览审阅、真实 Codex 验收是三个独立结论，必须分别记录。**

本文只定义检查方法和门槛，没有预填通过结果。真实记录放在 `reviews/`，不是写在这份标准里。

## 状态规则

单项结果只使用 `not-run`（未做）、`pass`（有证据通过）、`fail`（不通过）、`blocked`（无法完成并注明原因）、`not-applicable`（有具体不适用理由）。看不到或无法触发的状态是 `blocked` 或 `not-run`，不是 `pass`。

一个已构建的包在全部门槛满足前均为 `candidate`。发现任一硬门槛失败，当前 revision 记为 `rejected`，后续修改使用新 revision；不能删掉旧失败记录后把相同编号改成通过。只有三层验收均完成且用户确认真实效果，才可提出 `accepted`；版本发布与第三方许可判断另行记录。

## 第一层：自动检查

使用当前版本的 `tools/pet_tool.py validate`，把完整报告保存到该轮目录。以下结果应能复现：

| 检查 | 门槛 | 失败后动作 |
|---|---|---|
| 原生包 | `pet.json` 可读取，v2 图集路径存在且在包内 | 修复配置或打包 |
| 图片结构 | 静态 WebP，可解码为带透明信息的图像；1536 × 2288 | 重新导出 |
| 格子布局 | 8 × 11，每格 192 × 208；各行有效格数为 6/8/8/4/5/8/6/6/6/8/8 | 修正帧数和排列 |
| 非空约束 | 全部 73 个有效格均有可见角色；15 个余格全透明 | 退回构建，不允许“某格会少播” |
| 原版保留 | 除 idle/waiting/running 外，基线有效格可见像素不变；透明 RGB 清零可单独记录 | 找出意外变化并重建 |
| 可追溯 | 记录基线、替换素材、工具版本、产物哈希和构建命令 | 补全可复核记录 |
| 安装一致性 | 待安装包与已复制候选目录内容哈希一致 | 重新复制或排查缓存 |

若当前工具尚未覆盖某项，由人工补充检查并明确方法，不能因为脚本退出码为 0 就把未实现的检查标为通过。边框、颜色统计和像素差异不能代替人体、身份与表演判断。上游自带 `validation.json` 只是历史结果，不作为本轮证据。

## 第二层：视觉预览

使用同一套候选源文件和最终图集，分别看原版/候选对照、逐帧格子和原生时序。每一行都需指出对应证据；自动生成的联系表也需要真的看过才算审阅。

| 维度 | 硬门槛 | 观察方式 |
|---|---|---|
| 身份与脸型 | 三个精修状态及相邻基线状态仍是同一个八奈见；脸型、眼间距、发型、蝴蝶结与制服不漂移 | 原版/候选同尺寸并排，逐帧比较 |
| 肢体连续 | 无多余/消失的手臂、手、脚；前后遮挡和袖口连接成立 | 每一帧检查，并查看相邻帧 |
| 道具连续 | 道具数量、持握手、轮廓、大小与透视不突变；没有物件无故出现或消失 | 带道具的全部帧逐格检查；无道具注明不适用 |
| 尺度与锚点 | 三个站姿状态脚底及无意横移不超过设计的 2 px 门槛；比例变化满足设计约束 | 192 × 208 原生格、基线辅助线、数值记录 |
| 透明边缘 | 深浅底没有明显色边、孔洞、残影；发梢、鞋与手不被裁断 | 浅底、深底、棋盘，100% 与放大观察 |
| 小尺寸可读 | 96 × 104 和 48 × 52 下角色可辨认，三个状态有可理解差异，脸不会被道具挡住 | 不依赖放大和文字标签判断 |
| 原速节奏 | idle 不像慢速挤压或长闭眼；waiting/running 不急促抽动 | 原生速度观看，不以慢放替代 |
| 循环与退出 | 尾帧接首帧无跳变；非 idle 三轮后回 idle 不出现换脸、突变尺度或悬空 | 每个精修状态至少看三次进入/三轮/回待机过程 |
| 连续观看 | idle 原速至少 60 秒，没有周期性闪烁或明显干扰；其他状态三轮循环不累积视觉错误 | 保持真实播放，不拖动帧序列 |
| 保留动作相容 | 新旧状态切换时画风、头身比与基线一致；全部保留动作和 16 朝向可辨识 | 浏览全部行并跨状态比较 |

任一项为 `fail`，本轮候选即退回。主观“更喜欢原版”同样应记录具体原因，如眼睛过大、笑容消失、动作太忙；不能用“技术检查都通过”否定这一反馈。

## 第三层：真实 Codex 验收

预览器无法证明真实宿主中的事件映射、缓存、透明显示和实际使用感受。本次工具环境限制自动控制 Codex 界面，因此这一层由用户手动切换候选、观察并反馈；这只是实际验收的操作限制，不构成跳过标准的理由。

1. 记录 Codex 版本、macOS 版本、屏幕缩放、候选 revision 与安装哈希。
2. 在设置里的 Mini / My pets 选中“八奈见杏菜·精修”，显示 Mini。记录是否能看到候选；若刷新后仍是旧图，不把旧图效果当成候选结果。
3. 在浅色和深色应用背景上查看轮廓、脚底位置和小尺寸脸部；记录实际显示尺寸或足够辨识的截图。
4. 保持 idle 至少 60 秒，观察循环、闭眼停留、漂移与打扰感。
5. 在实际任务中观察工作、等待和返回 idle。只记录真正看到的状态；无法安全触发某状态就保留未验收，并说明缺少什么条件。
6. 观察原有拖动/移动/朝向或其他可实际触发动作，确认新包没有引入空白或错误行。不要为验收伪造失败任务、发送外部消息或修改应用代码。
7. 至少完整使用一个短任务或连续 10 分钟，记录是否愿意长期保留。报告具体问题对应的状态、帧或发生时刻。
8. 给出明确结论：可接受、需修改或未完成。用户没有反馈，不等于默认接受。

真实验收失败时，用户可以先切回原版；修复后安装新的候选并重做受影响项目。不能因为安装成功就改成 `accepted`。

## 每轮审阅记录

建议一轮一个目录：`reviews/<日期>-<候选编号>/`，例如日期后跟自增的 `candidate-001`。这只是命名格式，不代表已有该轮结果。

该目录至少包含：

- `review.md`：审阅者、时间、候选编号、上一轮编号、宿主版本；本轮目标；三层结果分别列出。
- `manifest.json`：上游 commit、输入/输出相对路径与 SHA-256、构建工具 revision 或文件哈希、完整构建参数。
- `validation.json`：本轮自动检查原始输出。
- 视觉证据：实际审阅使用的联系表、深浅底截图、问题帧或短录屏；不要存 token、账户信息和无关个人窗口。
- `issues.md`：每个问题的 ID、状态/帧、观察到的现象、对应门槛、严重程度、预期修复、复查结果。
- `decision.md`：保留 candidate、拒绝或接受的真实原因，以及下一步；未执行步骤明确标出。

不要求为了凑文件填写空壳“通过报告”。文件可合并，但上述信息必须可追踪；原始失败证据不覆盖。审阅模板只能放说明和空字段，不能给状态默认值 `pass`。

## 退回与复查

1. 锁定失败的候选哈希，在 `issues.md` 标出具体状态与帧，写清楚肉眼看到的问题，不只写“不够好”。
2. 身份失败先修参考和整行；肢体/道具失败修相关连续帧；锚点和色边问题先定位源素材，再做可追踪调整。
3. 输出新 revision 并重新构建，保留其余基线，重新执行自动检查。
4. 重看问题帧、相邻帧、循环接缝与回 idle；新改动影响的项目必须重验，已有无关证据可以引用但注明沿用理由。
5. 重新安装的候选由用户完成实际复查。未满足门槛就继续 candidate，不为了凑版本号降低门槛。

若当前生成方式反复无法保持同一角色，应缩小动作幅度、拆成逐行修复或改用人工绘制，不以扩展范围掩盖 v0.1 的核心问题。
